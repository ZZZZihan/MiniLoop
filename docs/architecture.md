# MiniLoop 架构与边界

## 状态与目标

本文是设计方案，所述模块与接口尚未实现。当前代码仅包含可导入的空包。

目标是把一次模型驱动的工具执行过程拆成可理解、可检查的部件。首版采用串行工具执行和单个模型适配器；先获得最小真实调用证据，再按失败情形补齐运行控制。

## 消息与工具流

1. 接收任务，建立消息历史和本次运行标识。
2. 检查预算后请求模型，记录响应。
3. 若响应包含工具调用，校验工具名、参数和调用标识，按返回顺序串行处理。
4. 将每个工具结果与对应调用 ID 配对后加入历史，再次请求模型。
5. 模型不再请求工具并给出答复时结束；错误或预算条件也可结束执行。

模型决定请求哪个已提供工具；实际执行权属于程序。未知工具和错误参数不能到达副作用操作。可返回模型继续处理的工具错误与必须终止的运行时错误，应在实现中分别列明。调用 ID 缺失、重复或不匹配时不得猜测关联。

## 计划工具

| 工具 | 首版行为 | 限制 |
| --- | --- | --- |
| `read_file` | 读取演示工作区内允许文件 | 限定根目录、文件大小和输出长度；验证解析后的路径 |
| `propose_patch` | 产生待确认的源码差异 | 不直接写文件；差异对应明确文件及原始内容 |
| `apply_patch` | 按确认应用指定差异 | 只修改允许源码；内容改变后旧确认失效；测试与评分文件不可修改 |
| `run_tests` | 执行案例预先配置的测试入口 | 不接受模型给出的任意 shell 字符串；记录退出码和输出 |

首个任务只做 `read_file`。代码修复阶段再引入其余工具，并使用演示副本。路径检查、命令枚举不等于操作系统沙箱；在未实现并验证执行隔离前，不声明能够安全运行任意外来代码。

## 预算与终态

计划至少限制模型调用次数、工具调用次数和总耗时，并给每个外部请求或子进程设置超时。调用前检查剩余预算；启动操作时使用剩余时间限制，避免只在调用完成后才发现超时。是否实际可取消运行中的请求，需要用对应适配器验证。

计划终态包括：`completed`、`step_limit`、`time_limit`、`model_error`、`protocol_error`、`cancelled`、`runtime_error`。最终枚举以实现和验证为准。

`completed` 仅表示模型正常结束循环，**不表示任务答案正确或代码修复成功**。工具返回错误后，若协议允许且预算足够，可以交还模型决定下一步。所有重试必须有上限，并纳入调用数和耗时。

## 轨迹与回放

计划事件字段包括 `schema_version`、`run_id`、`sequence`、事件类型、模型/工具标识、调用 ID、参数、结果或错误、耗时与终态。保留准确输入输出；认证密钥、请求认证头和无关环境变量不得写入轨迹。确需脱敏时记录处理方式，不能默默改变影响评分的内容。

JSONL 回放只解析并显示已记录事件：不请求模型、不实例化执行工具、不重新运行命令、不恢复任务。会话中断恢复、恰好一次副作用和运行中崩溃恢复均不在首版承诺内。损坏或截断记录要给出明确提示，不能补造缺失事件。

## 依赖策略

当前空包没有运行时依赖。实现时选择一个模型 API/SDK；参数校验可以根据实际接口采用必要的校验库。不要为尚未实现的功能提前安装框架、数据库、Web 服务或多模型适配集合。
