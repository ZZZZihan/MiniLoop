# MiniLoop 验证与评测协议

## 当前状态

**本项目尚无测试实现、评测数据、执行轨迹或成绩。** 下文为待实现协议，不存在已通过的测试或可报告的成功率。

## 两类证据分别回答什么

| 验证层 | 输入 | 回答的问题 | 不能推出 |
| --- | --- | --- | --- |
| 确定性协议验证 | 预设模型响应、工具返回和受控失败 | 调用配对、参数校验、预算和错误处理是否按约定工作 | 真实模型能完成任务 |
| 真实模型任务评测 | 冻结任务、真实模型、实际工具环境 | 给定模型与内核在这些任务上完成了什么 | 任意任务泛化、生产可靠性或上游榜单成绩 |

两类结果分别存储和报告，运行入口需显式选择模式。真实模式缺少配置或请求失败时必须报错，不得悄悄切换为替身。协议验证中可以模拟模型响应，真实评测中不得用预录答案冒充模型调用。

## 确定性协议情形

计划至少覆盖：

1. 模型请求工具、取得返回后正常结束。
2. 工具参数缺失或类型错误，副作用未发生。
3. 未知工具，返回明确结果或终止原因。
4. 工具超时，执行停止方式与结果明确。
5. 模型接口错误，重试有界并计入预算。
6. 模型持续请求工具，在预算上限停止。
7. 用户拒绝修改，演示文件保持不变。
8. 调用 ID 缺失、重复或不匹配，不执行错误配对。
9. 一轮多个工具调用，结果逐个关联。
10. JSONL 只读回放，模型与工具执行次数均为零。

这些是待实现的行为用例，不代表测试数量目标。断言应检查实际行为和副作用，不仅检查日志字符串或镜像实现的内部步骤。

## 真实模型任务与分组

从一个可稳定复现的小型修复任务开始，再按实际进展扩充；5–8 个独立案例只是初始规划。每例需要：

- 唯一 `case_id`、任务说明和起始文件。
- 原始故障、允许修改范围、固定测试入口及验收条件。
- 案例与测试内容哈希、Python 与依赖版本、参考来源。
- 人工确认可行的参考修复；参考答案不提供给运行中的模型。
- 分组标记：开发或正式评测；同源任务的轻微改写保持同组。

先在开发案例调试；运行正式评测前冻结任务、实现提交、提示词、模型标识、预算、允许操作与评分规则。未达到足够独立案例数量时报告真实数量，不虚构大样本。正式结果用于针对性修改后，相关案例应转为开发材料，不能继续称为未见测试。

## 修复成功判定

必须同时满足预先约定的测试通过、原故障消失、允许修改范围及目标功能约束。模型不能改评分测试、删掉待修功能或放宽约束来获得通过。执行固定入口仍需检查实际加载的测试内容，避免只看一个退出码。

模型正常结束循环与代码修复成功分开记录。超时、预算耗尽、模型错误和验证失败都保留在正式任务分母中；明确的缺少信息、拒绝修改等行为情形另设验证集合，不临时挪动案例改善成绩。

如评测需要自动确认修改，提前公布仅针对允许文件和操作的固定批准规则，不能根据参考答案决定批准哪个方案。确认逻辑的接受、拒绝和内容变化在协议验证中另行检查。

## 记录与指标

| 项目 | 记录规则 |
| --- | --- |
| 完成数 | 报告 `完成案例数 / 全部正式修复案例数`；没有实际运行就写“未测” |
| 退出状态 | 正常结束、预算、时间、模型或协议错误分别计数 |
| 调用次数 | 记录实际模型调用、工具调用及重试；约定调用失败如何计数 |
| 耗时 | 记录端到端和关键工具耗时，成功与失败均保留 |
| 用量 | 使用接口实际返回的 token/费用信息；未提供则标为未知 |
| 文件变化 | 保留前后差异和测试文件完整性检查结果 |
| 失败原因 | 原始轨迹与归类同时保留，不能仅保留摘要 |

每例保存首次运行。若增加重复运行，事先说明规则，逐次报告，不能挑最好一次。小样本结果只说明已固定任务集上的表现。

## 对照与发布

第一阶段先验证内核行为和任务可完成性，不要求立即跑大型榜单。之后若比较两个实现，保持任务、模型、提示词、工具、预算和评分器一致，并说明唯一变化；若这些条件同时变化，只报告整套方案结果，不归因于某个机制。

评测报告应包含执行提交、配置、逐例结果、完整失败记录和运行限制。确定性替身报告与真实模型报告分开；项目初始化或包导入成功不能记为内核验证通过。
